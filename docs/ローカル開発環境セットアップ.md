# ローカル開発環境セットアップ

RaiseChat をローカルで動かすための手順。

## 前提ツール

| ツール | バージョン(動作確認済み) | 用途 |
|---|---|---|
| Java | 21 | バックエンド(Spring Boot 3.5) |
| Maven | 3.9 | バックエンドのビルド・テスト |
| Node.js | 24 | フロントエンド(Vite + React) |

データベースはSQLite(ファイルで動く)なので、別途のインストールは不要。

## 初回セットアップ

```bash
git clone https://github.com/kiyota7/raisechat.git
cd raisechat

# バックエンド: 依存ライブラリを取得してビルドが通ることを確認
cd backend && mvn -q compile && cd ..

# フロントエンド: 依存パッケージをインストール
cd frontend && npm install && cd ..
```

## 起動(ポートは固定)

| 対象 | ポート | コマンド |
|---|---|---|
| バックエンド | **8080** | `cd backend && mvn spring-boot:run` |
| フロントエンド | **5173** | `cd frontend && npm run dev` |

ターミナルを2つ使い、それぞれ起動する。起動後は http://localhost:5173 を開き、新規登録(ユーザーID+パスワード)から始める。

**ポートを変えてはいけない理由**

- フロントエンド(`frontend/vite.config.ts`)は、`/api`・`/uploads`・`/ws` を `http://localhost:8080` に中継する設定になっている。バックエンドが8080以外で動くと、画面は表示されるのにAPI通信とWebSocketだけが失敗する。
- フロントエンドは `strictPort: true` のため、5173が使用中だと、別のポートに移らずに起動に失敗する。

## ポートが使用中のとき

別のポートに逃がさず、使用中のプロセスを特定して停止する。

```bash
# 使用中のプロセスを確認(PIDが分かる)
lsof -i :8080 -sTCP:LISTEN
lsof -i :5173 -sTCP:LISTEN

# 内容を確認してから停止する(何のプロセスかを見て、関係ないものは止めない)
kill <PID>

# 解放されたことを確認(何も表示されなければ空いている)
lsof -i :8080 -sTCP:LISTEN
```

`kill` で止まらないときだけ `kill -9 <PID>` を使う。止めてもすぐ同じポートで別のプロセスが立ち上がる場合は、何がポートを掴んでいるかを調べて解消する。

## 起動の確認

- **バックエンド**: 次のコマンドで `405` などのHTTPステータスが表示されれば、接続できている(起動済み)。接続できないときは `000` と表示される。
  ```bash
  curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/api/auth/login
  ```
  ヘルスチェック専用のエンドポイントは用意していない(ログインAPIにGETで接続し、応答があるかを見ている)。
- **フロントエンド**: ブラウザで http://localhost:5173 を開き、ログイン画面が表示されること。
- **WebSocket**: ログイン後、別のユーザーの投稿が再読み込みなしで反映されれば、接続できている。

## 2人のユーザーで動作を確認する

ログイン状態はブラウザの `localStorage` に保存されるため、**同じブラウザの別タブは、同じユーザーとして動く**。2人で試すときは、次のように分ける。

- 通常のウィンドウとシークレットウィンドウ
- 別のブラウザ(ChromeとSafariなど)

## データの場所と初期化

| 内容 | 場所 | git管理 |
|---|---|---|
| データベース(SQLite) | `backend/raisechat.db`(`-wal` などの付随ファイルを含む) | 対象外 |
| 添付ファイル・アバター | `backend/uploads/` | 対象外 |

初期状態に戻したいときは、**バックエンドを停止してから**、上の2つを削除する(次回の起動時に、テーブルが自動で作り直される)。ユーザーやメッセージはすべて消えるので、必要なデータがないことを確認してから行う。

## 設定(環境変数)

| 環境変数 | 内容 | 既定 |
|---|---|---|
| `JWT_SECRET` | ログイン用トークンの署名鍵。本番では必ず変更する | 開発用の固定値 |
| `APP_STORAGE_TYPE` | 添付ファイルの保存先 `local` / `s3` | `local` |
| `APP_STORAGE_S3_BUCKET` など | S3モードの設定。詳細は[README](../README.md)の「添付ファイルの保存先(S3)」 | - |
| `APP_LOGIN_MAX_FAILURES` など | ログイン試行の制限。詳細は[README](../README.md)の「認証のセキュリティ」 | 5回 / 15分 |
| `APP_CLUSTER_MODE` など | 複数サーバー(`redis`)。詳細は[README](../README.md)の「複数サーバーで動かす」 | `memory` |
| `SPRING_PROFILES_ACTIVE=postgres` など | PostgreSQLで動かす。詳細は[README](../README.md)の「PostgreSQLで動かす」 | SQLite |

## テストとCI

```bash
# バックエンド
cd backend && mvn test

# フロントエンド(リント / テスト / ビルド)
cd frontend && npm run lint && npm test && npm run build
```

テストは、既定ではSQLiteで動く。PostgreSQLで実行するには、環境変数 `TEST_DB_URL` などを指定する(詳細は[README](../README.md)の「PostgreSQLで動かす」)。

複数サーバーのテスト(`ClusterRedisTest`)は、Redisが `localhost:6379` で動いているときだけ実行され、なければ飛ばされる(Redisは、`docker run -d --name raisechat-redis -p 6379:6379 redis:7-alpine` で起動できる)。

フロントエンドのテストは、Vitest + Testing Library(jsdom)で、サーバーを起動せずに動く。`Chat` のテストは、`api` と `realtime`(WebSocket)をモックして、チャンネル切り替え・入力中表示・オンライン表示・プロフィール変更の反映などを確認する。

PRと `main` へのpushでは、GitHub Actionsが同じ内容を自動で実行する(`.github/workflows/ci.yml`)。

## トラブルシューティング

| 症状 | 原因と対処 |
|---|---|
| 画面は出るがログインや投稿ができない | バックエンドが起動していない、または8080以外で動いている。上の「起動の確認」とポートの確認を行う |
| フロントエンドが `Error: Port 5173 is already in use` で起動しない | 5173が使用中。「ポートが使用中のとき」の手順で、プロセスを停止する |
| `Web server failed to start. Port 8080 was already in use.`(バックエンド) | 8080が使用中。同上 |
| 他のユーザーの投稿がリアルタイムで反映されない | WebSocket(`/ws`)に接続できていない。ブラウザの開発者ツールのネットワークで `ws` を確認し、バックエンドの再起動後は自動で再接続されるまで数秒待つ |
| ログインで「ログインの試行回数が多すぎます。15分ほど…」と出る | 失敗が続いて制限された(正しいパスワードでも拒否される)。開発中は、**バックエンドを再起動**すると、失敗回数が消える(メモリ上で管理しているため) |
| 2タブで別のユーザーとして試したのに、同じユーザーになる | ログイン状態がタブ間で共有されるため。シークレットウィンドウか別ブラウザを使う |
