# 本番デプロイ手順(1台のサーバー + Caddy で自動HTTPS)

`docker-compose.prod.yml` を重ねて、1台のサーバーで RaiseChat を HTTPS 公開する手順。
構成: 利用者 →(HTTPS 443)→ **Caddy**(証明書の取得・更新、TLS終端)→ nginx(画面と中継)→ バックエンド(既定2台)→ PostgreSQL / Redis。
公開するのは 80(→443への転送と証明書の取得)と 443 だけで、nginx・バックエンド・DBは外に出さない。

## 1. 用意するもの

- Linux のサーバー1台(VPS や EC2 など。目安: 2 vCPU / 2GB メモリ以上)。Docker と Docker Compose(v2.24 以上)を入れる
- 独自ドメイン。DNS の A レコード(IPv6 なら AAAA も)を、サーバーの IP に向ける
- サーバーの 80/tcp、443/tcp、443/udp(HTTP/3)を、外から開ける(セキュリティグループやファイアウォール)

## 2. 設定(.env)

```bash
git clone https://github.com/kiyota7/raisechat.git && cd raisechat
cp .env.example .env
```

`.env` に、次を設定する(`.env` は git に入れない)。

| 名前 | 内容 |
|---|---|
| `DOMAIN` | 公開するドメイン名(例 `chat.example.com`) |
| `JWT_SECRET` | ログイン用の署名鍵。`openssl rand -base64 48`。32バイト未満や開発用の既定値だと、バックエンドは起動しない |
| `POSTGRES_PASSWORD` | DBのパスワード。`openssl rand -base64 24` |
| `BACKEND_REPLICAS` | バックエンドの台数(既定2) |

## 3. 起動

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.prod.yml ps
```

初回は、Caddy が Let's Encrypt から証明書を取得するので、1分ほどかかることがある。`https://<DOMAIN>/` を開いて、登録・ログインできれば完了。
証明書の取得に失敗するときは、次を確認する(ログは `docker compose ... logs caddy`)。

- DNS がサーバーの IP を向いている(反映まで時間がかかる場合がある)
- 80/443 が外から開いている
- 取得に何度も失敗すると、Let's Encrypt が一時的に制限をかける。直るまで待つ

## 4. 仕組み(確認ポイント)

- **HTTPS / wss:** 画面もAPIもWebSocketも、すべて同じドメインの 443 を通る。HTTP(80)は 308 で HTTPS に転送する。`Strict-Transport-Security`(HSTS)を付ける
- **接続元のIP:** Caddy が付けた `X-Forwarded-For` を nginx が受け取り、バックエンドへ渡す。nginx は外に公開していないので、外から偽の値は入れられない(Caddyも、外からの値を捨てる)
- **WebSocketの接続元(Origin):** 画面と同じオリジンだけ許可する(追加の設定は不要)
- **データの置き場所:** `pgdata`(DB)、`uploads`(添付ファイル)、`caddy_data`(証明書)の Docker ボリューム

## 5. 更新

```bash
git pull
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

DBのスキーマは、バックエンドの起動時に Flyway が自動で更新する。

## 6. バックアップ

```bash
# DB(日付付きのファイルに保存)
docker compose -f docker-compose.yml -f docker-compose.prod.yml exec -T postgres \
  pg_dump -U raisechat raisechat | gzip > raisechat-$(date +%F).sql.gz

# 添付ファイル
docker run --rm -v raisechat_uploads:/data -v "$PWD":/out alpine tar czf /out/uploads-$(date +%F).tar.gz -C /data .
```

復元は、`gunzip -c raisechat-日付.sql.gz | docker compose ... exec -T postgres psql -U raisechat raisechat`(空のDBに対して)。
`caddy_data` を消すと、証明書を取得し直す(取得回数の上限に注意)。

## 7. 複数のサーバーに増やすとき

- 添付ファイルは、ホストをまたぐと共有できないので、S3 に切り替える(README の「添付ファイルの保存先」)
- DB・Redis は、マネージドサービス(RDS / ElastiCache など)に移し、`SPRING_DATASOURCE_URL` と `SPRING_DATA_REDIS_HOST` を差し替える
- 入口は、ロードバランサ(ALB など)でTLSを終端してもよい。そのときは、nginx の `proxy-trust` の設定(`frontend/proxy-trust.caddy.conf`)を、そのロードバランサの経路に合わせる

## 8. ローカルでの検証

ドメインなしで、同じ構成を試せる。`DOMAIN=localhost` にすると、Caddy が内部CAの証明書(ブラウザは警告を出す)で HTTPS を提供する。

```bash
DOMAIN=localhost docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
curl -k https://localhost/api/me      # 401(未ログイン)なら、HTTPSの経路は通っている
```

開発用の `docker compose up`(http://localhost:5173)とは、同時に使わない。
